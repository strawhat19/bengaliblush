# Bengali Blush Feature Flags

The connected feature provider shares one server-confirmed Firestore singleton. It exposes saved global settings separately from effective viewer flags. The initial keys are `themeToggle`, `marquee`, `notifications`, and `contact`. No flags are stored in browser preferences.

The stable document is `featureSettings/FeatureSettings_1_Global_4_23_PM_10_12_26_b39e4e10-d4d7-41cf-9c5f-40a6a4703e90`, generated once using the existing `createRecordId` helper. Its identity is shared by source and rules. It has `id`, `number: 1`, `name: Global`, `type: FeatureSettings`, `version: 1`, server timestamps `created_at`/`updated_at`, and `features`. Each feature stores `{ enabled, description, audience: { roles, plans, planMode: minimum } }`. Roles are `guest`, `owner`, `admin`, and `subscriber`; `null` allows all roles and `[]` allows none.

Exact public singleton reads are allowed; listing and deletion are denied. Only the currently active Owner may create/update it. The service verifies the Firebase UID, current account mapping and authoritative account inside the transaction; rules apply the same Owner boundary. Initial creation atomically writes `counters/featureSettings` with `{ number: 1, record_id: <singleton ID> }`. Settings and counter validate each other. Later edits retain identity, number and created time, and update only feature values and the updated timestamp.

A server-confirmed absent singleton enables the four initial defaults for an eligible viewer. Cached/pending snapshots never establish initial settings or successful persistence. The provider uses the shared authenticated account and its active Owner capability for management visibility, avoiding a second identity observer that can disagree with the existing session. The shared account provider exposes session-load errors separately from action errors, preventing an unresolved account from becoming Guest access without hiding controls after an unrelated failed action. Saves and protected feature operations independently verify the current mapping, Firebase UID, role and status; malformed mapping status fields fail those authoritative checks. Signed-out viewers use the explicit Guest baseline. Loading, denied settings reads, malformed data, inactive accounts, and listener failures disable effective flags. The last confirmed saved row remains visible after a read/write failure; it is never replaced by device-only settings. Retry reattaches failed listeners. Owner edits target global values independently of that Owner's own audience eligibility; Owner management visibility remains available independently of a settings-read failure so the protected view can show the actual settings error and offer retry.

Public notification reads and contact creation independently evaluate current settings at the service/rules boundary. Contact transactions read the current singleton and authoritative account before allocation. Notification subscriptions stop immediately when disabled, ineligible, disposed, or moved to another session. Public notification queries request the latest 100 published records ordered by number; management uses its existing bounded pages. Rules retain separate authorized notification management and private submission review capabilities. The existing notification read preferences remain device scoped or visit scoped according to the existing storage setting; this change does not implement account-private read-state persistence or delivery. Contact intake retains its existing transaction-based allocation; retry idempotency and per-person abuse limits are separate work.

Bengali Blush currently has no saved paid plan catalog, public rank projection, or trusted plan entitlements. `tiers` is therefore empty, and paid plan controls report the missing connection. `plans: null` means Free And Above. New paid thresholds are rejected by both the service and rules. A compatible previously saved single-slug minimum may be retained or cleared for recovery, but remains unavailable for every viewer until trustworthy catalog ranks and entitlements exist. Typed rank helpers order future metadata by nonnegative catalog `displayOrder`, then positive app-owned `number` and stable ID; arbitrary viewer plan strings do not grant access. No paid offers, names, assignments, checkout or entitlement mechanism were invented.

`firestore.indexes.json` includes the public notification composite (`status` ascending, `number` descending) and exempts the exact-read feature settings payload from unused indexing.
